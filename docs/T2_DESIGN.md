# T2 — Safety Block: проект решения

Источники: ТЗ_T2 (см. `~/ros2_ws/docs/TZ_SUMMARY.md`), код симулятора организаторов
(`go1_simulation/scripts/go1_mujoco.py`, `go1_unitree_bridge/go1_unitree_bridge/core.py`, коммит `96768c1`).

|---|---|---|

Проверка коллизий (измерено на хосте, MuJoCo 3.3.7): стандартные правила MuJoCo на **`go1.xml` без пола**
(маски contype/conaffinity, фильтр родитель/потомок, одно сваренное тело) дают **ровно 655 пар = `checked` в CSV**
(id в CSV — от `scene.xml`, сдвиг на 1 из-за пола). `geom_margin = 0.001` у всех геометрий → `mj_collision`
возвращает контакты при расстоянии < 1 мм; проникновение = `−contact.dist`.
Стоимость `mj_kinematics + mj_collision`: **~17 мкс на позу** (i7-12700H, 1 поток).

## 2. Решения
### Интерфейс и QoS
- Вход `/lowcmd_bare`: подписка **BEST_EFFORT** depth 10 — совместима и с RELIABLE, и с BEST_EFFORT издателем Judge.
- Выход `/lowcmd`: издатель **RELIABLE** depth 10 — совместим с подпиской сима (RELIABLE) и любой подпиской Judge.
- `/lowstate`: BEST_EFFORT, нужен только первый кадр (латчим стартовую позу), затем подписка удаляется (экономия CPU на 500 Гц).
- `use_sim_time=true`; все тайм-ауты — по sim time.

### Потоки и частота (после аудита на медленном CPU)
Аудит у участника (CPU медленнее) нашёл паузы /lowcmd 120–130 мс (> 100 мс ТЗ): публикация, разбор входа и проверки
коллизий шли в одном потоке, бюджеты — числом вычислений. Теперь:
- **executor** (один поток): таймер публикации 200 Гц на steady-часах только отправляет готовые байты последней
  проверенной позы (`publish(bytes)` под коротким lock) — без вычислений; вход — raw-подписка в слот «последнее сообщение».
- **рабочий поток**: просыпается после каждой публикации, разбирает только последнее входное сообщение (кодек
  `lowcmd_codec.py`: смещения полей LowCmd найдены по меткам в сериализованном шаблоне, чтение — `numpy.frombuffer`,
  запись — заполнение шаблона; в разы дешевле Python-объектов на 20 моторов), двигает цель и проверяет пути
  с бюджетом **по времени** 1.2 мс за порцию; не успел — продолжит в следующей, а таймер публикует прежнюю позу.
- Следующая поза считается только после публикации предыдущей → шаг между соседними /lowcmd ≤ 4.5° при любой загрузке.
- `sys.setswitchinterval(1 мс)` — рабочий поток быстрее отдаёт GIL таймеру.
- **Немедленная публикация** (`immediate_publish`, по умолчанию): при входе 500 Гц таймер 200 Гц пропускал ~60 %
  безопасных команд (до выхода доходила лишь та, что совпала с тиком). Теперь колбэк входа для принятой команды сразу
  делает шаг ядра и публикует результат. Порядок публикаций = порядок расчёта: перед своей позой колбэк выпускает
  ещё не опубликованную позу рабочего потока; все публикации — под `out_lock`, в одном месте (`_publish_locked`).
  Таймер 200 Гц остаётся (ровность, удержание) и пропускает тик, если публикация была < 0.8 периода назад.
- Перенос на C++ (rclcpp + MuJoCo C API) не потребовался (и по решению капитана не делается).

| judge_sim, вход → | CPUS=1.0, 100 Гц | CPUS=1.0, 500 Гц | CPUS=0.5, 100 Гц | CPUS=0.5, 500 Гц |
|---|---|---|---|---|
| до: макс. пауза / баллы | 90 мс / 12 | 60 мс / 12 | 70 мс / 12 | 70 мс / 12 |
| после: макс. пауза / баллы | 20 мс / 12 | 10–20 мс / 12 | 30 мс / 12 | 50 мс / 12 |
Пауза — по sim time judge_sim (шаг /clock 10 мс); внутренний замер узла по wall: 5–6 мс. Проверка будет на мощном
сервере организаторов; обязательная приёмка — CPUS=1.0, вход 500 Гц: пауза ≤ 30 мс, 12/12 — выполнена (3 прогона).

### Частота
- Публикация по **таймеру 200 Гц на steady (wall) часах**, не по входу и не в потоке расчётов (см. выше). Почему не sim-таймер: `/clock` идёт 100 Гц,
  rcl-таймер по sim time срабатывает не чаще обновлений часов и «замирает», если `/clock` встал. Сим MuJoCo никогда
  не обгоняет реальное время → 200 Гц wall ≥ 200 Гц sim. Требование ТЗ: ≥ 50 Гц, пауза ≤ 100 мс sim.

### Выходное сообщение
- `motor_cmd[0..11]`: `mode = 0x0A` **всегда**; `q` — безопасная цель; `dq`, `kp`, `kd`, `tau` — из принятой команды,
  ограниченные диапазонами ниже; при удержании `dq = 0`, `tau = 0`.
- `motor_cmd[12..19]`: все поля 0 (`mode = 0` — не используются симом). Остальные поля LowCmd — нули/значения по умолчанию.

### Пределы (запас внутри пределов ТЗ)
| Поле | Диапазон | Обоснование |
|---|---|---|
| `q` | [q_min + 0.01, q_max − 0.01] рад по суставу | ТЗ_T2, запас 0.01 рад |
| шаг `q` между соседними `/lowcmd` | ≤ **4.5°** на сустав | ТЗ: ≤ 5° |
| `kp` | [0, 1000] | официальное уточнение организаторов (фильтр некорректных команд) |
| `kd` | [0, 100] | официальное уточнение организаторов |
| `dq` | [−20, 20] рад/с | официальное уточнение организаторов (совпало с нашим выбором) |
| `tau` | [−100, 100] Н·м | официальное уточнение организаторов; физический предел момента (±23.7 / ±35.55) симулятор применяет сам |
- Удержание (потеря входа и до первой команды): kp/kd — последние принятые, но если `kp < 5` → kp=40, kd=2 (как у сима):
  «держать» с нулевым kp нельзя.
- `NaN/±Inf` в любом из полей `q, dq, kp, kd, tau` **любого из 20** моторов → сообщение отбрасывается целиком,
  продолжаем публиковать последнюю безопасную цель. Конечные значения вне диапазонов — клип (в т.ч. `|q| ≥ 1e8` → предел).

### Движение к цели и самоколлизии
**Принятие новой цели (исправление «ловушки» из независимого ревью):** раньше блок шёл к любой клипнутой цели и
останавливался у препятствия; из такой точки прямой путь к следующей безопасной цели мог проходить сквозь корпус —
блок «застревал» (2 из 25 случаев), а ТЗ не засчитывает вечное удержание. Теперь:
1. цель сама в коллизии (> 0.25 мм) → отказ целиком сразу (1 вычисление);
2. прямой путь от текущей выходной позы до цели проверяется **целиком** (та же непрерывная граница) → свободен — исполняем;
3. перекрыт → **отход по истории**: кольцевой буфер опубликованных поз (сжатый: соседние записи соединены проверенным
   отрезком ≤ 4.5°); ищем точку истории (текущая поза, затем ~40 точек от новых к старым), из которой прямой путь к цели
   свободен, отходим к ней назад по истории (путь заведомо безопасен) и идём к цели;
4. не нашли за 20 000 вычислений → отказ (держим последнюю цель); повтор той же отклонённой цели — не чаще раза в 0.2 с.
Поиск пошаговый: сразу ≤ 300 вычислений (5–9 мс), затем по ≤ 250 за такт; пока он идёт, выход стоит и публикуется.
Замер (300 новых целей, половина случайных в пределах ТЗ): проверка при новой цели в среднем 8 мс, макс 15 мс;
вычислений в среднем 189; полный поиск с отходом — до ~7 400 вычислений за несколько тактов. Пауза потока ≤ 34 мс.

- Принятая цель = клипованный `q` входа. Выход идёт к цели по **прямой в пространстве суставов**; шаг за такт —
  доля прямой, при которой max|Δq_сустава| ≤ 4.5°.
- Каждый шаг проверяется **непрерывно, а не выборкой** (реализовано в `collision.py`): в нашей копии модели
  `geom_margin = 5 см`, поэтому `mj_collision` даёт расстояние d до всех пар ближе 5 см. Для каждой геометрии и сустава
  заранее посчитана граница R (сумма длин звеньев от оси сустава до центра геометрии + её радиус), откуда скорость
  изменения расстояния вдоль пути ≤ L. Из точки с расстоянием d идём на ds = (d + 0.5 мм)/L — на этом куске проникновение
  **нигде** не превышает 0.5 мм (Judge: > 1 мм — нарушение, проверяет выборкой 0.1°). Тест сверяет с выборкой 0.01°.
- Пошаговая проверка такта осталась как страховка (точка с проникновением > 0.25 мм не принимается); при проверке
  всего пути заранее упоров не бывает (в прогонах: 0).
- Стоимость (замер): покой 0.1 %, синус 2 %, случайные далёкие цели 4–6 % ядра на проверки; вдали от препятствий
  1–2 вычисления на такт. Весь контейнер: ~14 % ядра при входе 100 Гц, ~30 % при 500 Гц (накладные rclpy на сообщения).
- Вход обрабатывается в такте: callback только запоминает последнее сообщение и время, такт разбирает самое свежее
  (невалидное — отклоняется целиком, промежуточные валидные цели заменяются более новой).
- Коррекция цели (остановка у препятствия) — допускается ТЗ («скорректировать до безопасного значения»).
  «Принятой безопасной целью» для удержания считается точка, куда мы реально пришли/идём.

### Потеря входа
- Нет `/lowcmd_bare` > **0.3 с sim time** (ТЗ: 0.5 с) → удержание: `q` = текущая принятая цель (продолжаем довести рампу,
  если она не закончена), `dq = 0`, `tau = 0`, допустимые kp/kd. Поток `/lowcmd` не прерывается.

### Старт (до первой команды)
- Ничего не публиковать нельзя: Judge меряет поток `/lowcmd`, а сим после нашей первой публикации перестаёт держать сам.
- Решение: по первому `/lowstate` латчим измеренную позу (клип в пределы) и публикуем её как удержание с kp=40, kd=2 —
  физически то же, что делает сим. Латчим **один раз**, не следим за измерением (иначе поза «оседает» под весом).
- До первого `/lowstate` не публикуем (безопасная поза неизвестна). Если вход пришёл раньше `/lowstate` —
  стартовая точка = keyframe `home` (0, 0.9, −1.8), проверенная на коллизии.

### Запрет «вечного удержания»
- Любая безопасная команда двигает выход к ней (рампа ≤ 4.5°/такт), опасная — клипуется/останавливается у препятствия.

## 3. Проверка (результаты)
- Unit-тесты (без ROS, 79 шт.: + 60 циклов «опасная → безопасная», явная ловушка с отходом, стоимость проверки пути): пары = CSV, гарантия пути (выборка 0.01°), реальные позы с самоколлизией, пределы, рампа,
  NaN/Inf во всех полях и слотах, тайм-аут/удержание, старт, клип kp/kd/dq/tau — зелёные на хосте и в образе.
- `tools/run_judge_docker.sh` (judge_sim в соседнем контейнере): **12/12** при входе 50, 100 и 500 Гц;
  после исправления ловушки + 50 циклов «случайная → безопасная рядом с home»: 12/12, безопасные цели 50/50.
- `tools/run_with_organizers_sim.sh` (настоящий MuJoCo-сим организаторов через run_local.py): **12/12**, 50/50.
- Нативный запуск сима в WSL не делали: образ сима организаторов скачивается публично и работает в Docker
  (RTF 1.0) — это ближе к судейской среде, чем ручная сборка go1_ws на хосте.
- Найдено при проверке: прямой путь к клипнутой цели может проходить через самоколлизию (например, thigh 0.9 → 4.5 рад
  проходит сквозь корпус) — блок останавливается у препятствия; это допустимая ТЗ «коррекция».

## 5. Диапазоны организаторов и немедленная публикация (ветка improve/t2-ranges-passthrough, 20.11.2026)
Сравнение с main (`ec95520`, логика T2 = сданному `7f95a1a`), judge_sim в Docker; «без изменений» — доля команд безопасной
траектории, вышедших в /lowcmd побитово теми же (q/dq/kp/kd/tau, 12 приводов); CPU — контейнер решения, средн. / макс.

- Пауза меряется judge_sim по sim time с шагом /clock 10 мс; узел по wall-часам видит ≤ 6 мс. Вход 500 Гц, новый образ,
  6 прогонов в окончательном виде: 20–30 мс, все 12/12.
- **Найдено при сравнении:** main при входе 500 Гц в 7 из 12 прогонов 20.11 давал паузы /lowcmd 410–520 мс (9/12): узел
  сам фиксировал простой таймера публикации; вызов publish ≤ 1 мс, порция рабочего потока ≤ 2.5 мс, машина не подвисала

  не воспроизвелась ни разу. При 100 Гц у main проблемы не было. Сданный образ T1 содержит эту же логику T2.
- Цена: при входе 500 Гц CPU выше (каждая команда — полный шаг ядра и публикация), остаётся < 1 ядра при CPUS=1.0.
