## 1. Задача и контракт (ТЗ_T4, раздел 6)
Judge сам ведёт робота (Gazebo Classic 11 + CHAMP, Highlevel, `/cmd_vel`, lockstep), участник только оценивает
фактическое положение и ориентацию корпуса.

| Топик | Тип | Направление |
|---|---|---|
| `/cmd_vel` | `geometry_msgs/Twist` | Judge → Simulator (**мы не публикуем**) |
| `/joint_states` | `sensor_msgs/JointState` | Sim → решение |
| `/imu/data` | `sensor_msgs/Imu` | Sim → решение |
| `/scan` | `sensor_msgs/LaserScan` | Sim → решение (только режим lidar, QoS RELIABLE) |
| `/camera/...` (RGB-D 640×480, 15 Гц) | `Image`, `CameraInfo` | Sim → решение (не используем) |
| `/odom` | `nav_msgs/Odometry` | решение → Judge, `frame_id=odom`, `child_frame_id=trunk` |
| `/tf` | `tf2_msgs/TFMessage` | решение публикует `odom → trunk` |
| `/clock` | `rosgraph_msgs/Clock` | sim time |

- `/odom` и TF — **≥ 20 Гц sim**, согласованные поза и ориентация, корректные stamp и frame; NaN/Inf и
  ненормированные кватернионы запрещены. Начальная поза произвольна: Judge совмещает начальную оценку с истиной.
- Сценарий: неподвижная фаза → квадрат (4 прямых по 0,2 м/с, 4 поворота на 90° по 0,3 рад/с) → остановка →
  неподвижный интервал 10 с для дрейфа. Judge может замыкать курс по истине.
- Метрики: RPE — путь по истине режется на участки ≈ 1 м, ошибка `|Δp_odom − Δp_gt| / длина участка`, среднее по
  участкам; дрейф — изменение позы за 10 с неподвижности.
- Баллы (20): публикация `/odom` + TF ≥ 20 Гц — 3; RPE ≤ 50 % — 5; RPE ≤ 20 % — ещё 6; дрейф ≤ 0,10 м и ≤ 5° — 6.
- Запрещено: доступ к истине (`/odom/ground_truth`), воспроизведение заранее известной траектории вместо оценки.

## 3. Архитектура `src/go1_odometry`
Пакет из двух слоёв: расчёт без ROS (`core.py`, только numpy — тестируется на хосте) и тонкий ROS-узел (`node.py`).
Запуск: `/entrypoint.sh T4` → `go1_bringup/launch/t4.launch.py` → узел `go1_odometry` с `config/odometry.yaml`,
`use_sim_time=true`.

### core.py — `OdometryEstimator`
- **Входы** (сохраняют последнее валидное значение; NaN/Inf, неверная форма — отбрасываются и считаются в `rejected`):
  - `set_imu(t, quat, gyro=None)` — кватернион IMU (и угловая скорость для запасного режима `gyro`);
  - `set_joints(t, q)` — 12 углов в порядке `FR, FL, RR, RL × (hip, thigh, calf)`;
  - `set_contacts(t, mask)` — необязательная маска опоры (4 ноги), например по `/foot_force`.
- **Расчёт** `step(t)` — на таймере узла:
  1. Ориентация `odom ← trunk` = кватернион IMU (imu_link закреплён на trunk без поворота). При
     `heading_reference: world` курс мировой с первого сообщения.
  2. Прямая кинематика стоп по URDF сима (смещения бёдер ±0,1881 / ±0,04675 м, бедро 0,08 м, звенья 0,213 м)
     → положения стоп в осях `odom` относительно trunk.
  3. Вес опоры ноги `w = 1 − Δh / stance_height` (Δh — высота стопы над самой низкой, в обоих тиках); опорная стопа
     неподвижна в мире ⇒ смещение корпуса `Δx = −Δf`, взвешенное среднее по опорным ногам.
  4. ZUPT: стопы относительно trunk почти неподвижны и корпус не поворачивается ⇒ смещение 0 (защита дрейфа на стоянке
     от вибрации).
  5. Высота trunk — по опорным стопам + радиус стопы, сглаженная.
- **Выходы:** `position` (м, odom), `orientation` (x, y, z, w), `lin_vel`, `ang_vel` (в системе trunk, сглаженные),
  а также `stationary`, `weights`. Команды, траектория и истина не используются.

### node.py — `OdometryNode`
- Подписки: `/imu/data`, `/joint_states` (QoS RELIABLE, depth 10), `/clock` (через `use_sim_time`); `/foot_force` —
  только при `use_foot_force: true`. Колбэки только сохраняют сообщение; суставы сопоставляются по именам.
- Таймер расчёта `update_rate` (sim), публикация `/odom` и TF `odom → trunk` раз в `1/publish_rate` по sim time,
  с одним и тем же stamp (= текущее sim time); до прихода sim time и до первой валидной позы ничего не публикуется;
  публикуется только поза с конечными числами и |q| = 1 ± 1e-6.
- Переменные DDS (`ROS_DOMAIN_ID`, `RMW_IMPLEMENTATION`, `CYCLONEDDS_URI`, `ROS_LOCALHOST_ONLY`) не трогает.

### Режим lidar (`estimator.mode: lidar`; по умолчанию с ada5607)
**Источник ядра.** `lidar_core.py` — ядро одометрии, разработано командой «Кафедра проблем», BSD-3-Clause (остальной
пакет `go1_odometry` — MIT). Код ядра **не менялся**: добавлен только заголовок (источник, лицензия, список правок).
Узел источника (`odom_node.py`, подписан на `/go1_contacts`) не переносился. Тесты ядра перенесены в
`test/test_lidar_core.py` (без `test_recording` — ему нужна запись `.npz` формата источника).

**Алгоритм простыми словами.**
1. *Ориентация* (курс, крен, тангаж) — кватернион `/imu/data` как есть, курс мировой с первого сообщения. Для скана
   берётся ориентация на момент его штампа (интерполяция по истории IMU за 1 с); скан, пришедший раньше IMU, ждёт её
   в очереди (до 40 сканов; после долгой паузы IMU разбираются только сканы не старше 0,5 с).
2. *Сопоставление скана «точка–прямая».* Точки скана (0,15–10 м, NaN/Inf отбрасываются) поворачиваются ориентацией
   IMU в мировые оси, точки пола (ниже корпуса > 0,20 м) выкидываются; скан усредняется по ячейкам 8 см вдоль дуги, у
   каждой ячейки — нормаль поверхности (если окрестность плоская). Неизвестен **только сдвиг xy** (2 числа): поворот
   уже известен из IMU. Сдвиг ищется итерациями (≤ 8): пары «ячейка — ближайшая точка опорного скана» (не дальше 0,3 м),
   невязка вдоль нормали опорной точки, робастные веса Коши (масштаб 3 см). Меньше 30 пар — скан не используется.
3. *Опорный скан* — первый скан; сменяется, когда робот отъехал от него на 0,5 м или доля совпавших точек
   (невязка < 9 см) упала ниже 0,3.
4. *Вырожденные направления* (коридор, одна стена): если по оси информации меньше 5 % от суммы весов, вдоль неё сдвиг
   не уточняется — остаётся **прогноз по ногам**.
5. *Между сканами* выход — по скорости последних сканов; без сканов дольше 0,3 с — по пути опорных ног (кинематика
   по URDF, опорная стопа неподвижна в мире; через разрыв суставов > 45 мс путь не считается); нет и суставов дольше
   0,1 с — по последней скорости, не дольше 2 с.
6. *Стоянка*: если размах крена, тангажа и курса за 0,3 с < 0,5°, выход **замораживается** (на ходу рысь качает
   корпус ≥ 0,75°, стоя — ≤ 0,2°) и скорость сканов обнуляется.
7. *Плавное введение поправок*: поправка скана, выход из стоянки и смена источника выхода (сканы ↔ ноги) входят в
   выход с постоянной времени 0,2 с — без скачков позы.
8. Штамп назад в любом потоке — полный сброс ядра, повтор штампа — пропуск.

**Опора без контактов.** `on_contact` в нашем узле не вызывается (`/go1_contacts` не используем, см. раздел 5),
поэтому ядро всегда берёт опору по высоте стоп: нога опорная, если её стопа в мировых осях не выше самой низкой на
`CONTACT_Z = 0,02 м` (тесты `test_stance_by_foot_height_without_contacts`, `test_legs_stance_by_foot_height_without_contacts`).

**Раскладка суставов по именам.** Ядро ждёт порядок FL, FR, RL, RR × (hip, thigh, calf) (`LIDAR_JOINT_NAMES`), legs —
FR, FL, RR, RL; `/joint_states` приходит в своём (не алфавитном) порядке. Узел сопоставляет углы по **именам** для
каждого оценщика отдельно; нет хотя бы одного сустава — сообщение отбрасывается (`test_joint_order_by_names_and_kinematics_agree`,
`test_lidar_joints_by_name_and_world_heading`).

**Обёртка** `lidar_mode.py` (`LidarEstimator`): отбрасывает NaN/Inf и неверную форму входов (кватернион, 12 углов, штамп,
углы скана, пустой скан) со счётчиком `rejected` — дальности NaN/Inf допустимы, их отсеивает ядро; подаёт события
пакетом по штампам (при равных штампах IMU раньше суставов и скана); меряет время обработки сканов; выдаёт позу
только с конечными числами.

**Потоки.** Подписки: `/imu/data`, `/joint_states`, `/scan` (QoS **RELIABLE**: BEST_EFFORT-подписка от сима ничего не
получает), `/clock`; `/foot_force` в этом режиме запрещён (узел не стартует при `use_foot_force: true`).
- Колбэки только сохраняют: IMU и сканы — в очередь, суставы — последнее сообщение.
- Сопоставление сканов — в **отдельном рабочем потоке** (`lidar.worker_thread: true`): таймер 200 Гц sim передаёт ему
  входы и тик и **не ждёт** расчёта (`test_lidar_slow_matching_does_not_delay_publication`: сопоставление 0,3 с, тик < 50 мс,
  `/odom` без пропусков).
- Таймер публикует **последнюю готовую позу** рабочего потока с текущим sim time в stamp: xy и кватернион — ядра; z и
  угловая скорость — legs-оценщика, который считается и в этом режиме; линейная скорость — разность поз ядра в осях trunk
  (сглаживание `twist_alpha`). Ошибка расчёта в потоке не останавливает публикацию (идёт последняя валидная поза).
- В диагностике (`diag_period`) — число сканов (сопоставлено / пропущено / опорных / вырожденных), время сопоставления,
  возраст позы рабочего потока, очередь, отброшенные входы.

**Параметры** режима (таблица ниже): `estimator.mode`, `scan_topic`, `lidar.leg_scale`, `lidar.worker_thread`; пороги
ядра — константы в `lidar_core.py` (не параметры, чтобы ядро оставалось как в источнике).

**Включение** без смены дефолта: `ros2 launch go1_bringup t4.launch.py estimator_mode:=lidar` или `estimator.mode: lidar`
в `config/odometry.yaml`. После живой приёмки (вердикт «готово», 22.11) по умолчанию `lidar`; `legs` — запасной режим.

**Страховка на случай пропажи `/scan`** (`fallback.py`, `LidarFallback`; без ROS, узел только подаёт данные).
*Зачем:* ядро без сканов само идёт по своему пути ног, но заметно хуже нашего legs (офлайн bag B: ядро без сканов
18,6 %, legs 10,0 %), а после долгой паузы может не «поймать» опорный скан и остаться со сдвигом (B, 40 с: 0,57 м).
*Логика.* В режиме lidar параллельно считается наш `core.OdometryEstimator` (те же `/imu/data` и `/joint_states`;
он и раньше давал z и ω). Курс у обоих — мировой yaw IMU, поэтому сшивается только xy:
1. **lidar** — пока сканы идут: выход = поза ядра (+ затухающая поправка после возврата).
2. **→ legs** — `/scan` не приходил дольше `estimator.scan_timeout` = 1,0 с sim (по часам узла в момент прихода) или
   поза рабочего потока старше этого (поток завис): выход = выход в момент переключения + **приращения legs** — без
   скачка позы. Кватернион и twist — legs-оценщика (тот же кватернион IMU).
3. **→ lidar** — сканы снова идут без перерывов > 1 с в течение `fallback_resume_delay` = 0,5 с (ядро успевает само
   сопоставить первые сканы и ввести свою поправку): поправка = выход − поза ядра, затем она затухает экспоненциально
   с `fallback_blend_tau` = 1,0 с (как `BLEND_TAU` ядра, но медленнее: ≤ 0,25 м/с, ≤ 5 мм за тик 50 Гц).
   Если поправка больше `fallback_max_correction` = 0,25 м, она **не затухает**: выход = наша поза на возврате +
   приращения ядра. Ядро исправляет расхождение только в пределах `PAIR_DIST` = 0,3 м от своего прогноза; при
   большем расхождении его абсолютная поза сомнительна (B, 40 с: ввод поправки 0,42 м давал RPE 14,9 % вместо 8,8 %).
4. Штамп назад (сброс sim) — сброс страховки (снова lidar, без поправки); ядро сбрасывается само.
Расчёт лёгкий (несколько операций numpy на тик публикации), сопоставление сканов — по-прежнему в рабочем потоке.
Диагностика узла: `источник lidar|legs, переключений N, без сканов X с sim`. Узел в режиме lidar требует
`heading_reference: world` (иначе курс legs отличался бы от курса ядра). `lidar_core.py` не менялся (sha256 тот же).
Онлайн-калибровка масштаба и поворота legs по lidar пробовалась и отброшена: на B ошибка legs зависит от направления
поворота, калибровка ухудшила 15 с с 4,4 до 7,6 %.

## 4. Что запрещено и как это проверяется
- **Истина** (`/odom/ground_truth`, `/gazebo/*`, model/link states) в решении не читается. Белый список входов —
  `ALLOWED_INPUT_TOPICS = (/imu/data, /joint_states, /clock, /foot_force)` в `node.py`; узел падает при старте, если
  параметром задан другой топик.
- Режим lidar: `ALLOWED_INPUT_TOPICS_LIDAR = (/imu/data, /joint_states, /clock, /scan)`.
- Тесты `test/test_node.py`: подписки узла ⊆ белого списка в обоих режимах (legs — с `/foot_force` и без; lidar — с
  `/scan` RELIABLE, без `/foot_force`); `/cmd_vel`, `/cmd_vel_gated`, `/odom/ground_truth`, `/go1_contacts/FL`,
  `/gazebo/*`, камера как параметр — отказ в обоих режимах; в исходниках пакета нет запрещённых имён (cmd_vel, ground_truth, gazebo,
  go1_contacts, foot_contacts, camera, champ, model_states, link_states) и подписок вне `node.py`.
- `/cmd_vel` решение не публикует (воспроизведения командной траектории нет).
- Истина используется **только в стенде** (`tools/judge_t4.py`, `tools/dev_t4_offline_eval.py`) — для метрик и коррекции
  курса, как Judge. Стенд в образ не попадает. На живых прогонах стенд опрашивает граф: подписчик истины — только узел
  стенда, публикатор `/cmd_vel` — только стенд (ACCEPTANCE_T4).

## 5. Контакты — решение владельца (21.11)
- Опорные ноги определяются **по кинематике** из топиков контракта ТЗ (`/joint_states` + ориентация `/imu/data`).
- `/foot_force` — необязательный сигнал (параметр `use_foot_force`, по умолчанию выключен).
- `/go1_contacts/*` (`gazebo_msgs/ContactsState`) **не используем**, `gazebo_msgs` в образ не добавляем;
  `/foot_contacts` (champ_msgs) почти всегда False — тоже не используем.

## 6. Стенд самопроверки
### `tools/judge_t4.py` (только для разработки)
- **Режимы:** `live` — сим и решение уже запущены, стенд ведёт робота по пресету (`tz`: сторона 2 м, влево, коррекция
  курса по истине; `right`: 1,25 м, вправо; `tz_open`: 1,5 м без коррекции; `short`: 1 м), пишет `/odom`, TF и истину;
  `bag` — проигрывает bag разведки, оценку даёт образ решения (`--image`, `--cpus`) или заглушка (`--stub`);
  `reanalyze` — пересчёт метрик по `record.npz`.
- **RPE A** — разности в мировой системе после совмещения начальной позы (`--align pose`: перенос + поворот, ТЗ 6.2;
  `--align position` — только перенос, справочно как риск). **RPE B** — перемещение в системе начала участка своей
  траектории. Участки ≈ 1 м по горизонтальному пути истины, сглаженному 0,5 с; хвост короче 0,5 м не оценивается.
- **Дрейф** — изменение позы за 10 с неподвижности (положение и полный угол поворота).
- **Частота** — по `header.stamp` (sim), минимум окна 1 с; плюс проверки frame, NaN, |q|, монотонности stamp и
  `/odom ≡ TF` при одном stamp.
- Выход: `result.json` (PASS/FAIL по ТЗ и по порогам приёмки), `summary.txt`, `trajectory.png`, `record.npz`.
### `tools/run_t4_with_organizers_sim.sh`
Поднимает настоящий сим организаторов (`run_local.py --task T4`, headless, lockstep) и образ решения так же, как
судья (`--network host`, `/entrypoint.sh T4`), ограничивает CPU решения (`CPUS`, `docker update`), запускает
`judge_t4.py live` в том же домене, рядом — сторож памяти. Один сим за раз, запускать в tmux; прогон ~7–10 мин wall.

## 7. Ограничения и риски
- **Как Judge совмещает позу** (поворот или только положение) и что считает «путём» участка — `TODO(уточнить)` у
  организаторов. При курсе от 0 и старте с курсом ≠ 0 совмещение только положением давало RPE 40,5 % (bag B) и 50,3 %
  (bag C); с `heading_reference: world` — 11,1 % и 6,9 %, одинаково для обоих способов совмещения.
- **Длина стороны квадрата** и длительности фаз Judge неизвестны (ТЗ 6.3) — `TODO(уточнить)`; проверены 1,25–2 м.
- **RTF на ноутбуке ~0,2** (0,21–0,24 в живых прогонах): живой прогон долгий, статистика небольшая. Лимиты CPU/RAM
  в официальном прогоне неизвестны — проверяем с `CPUS=1.0`.
- **Режим lidar** — принят 22.11 и включён по умолчанию; `legs` остаётся запасным (`estimator.mode: legs`). Риски lidar: длинный
  коридор без поперечных стен (вдоль него — только ноги), открытое пространство без отражений (только ноги),
  нагрузка CPU выше legs: ≈ 33 % ядра против ≈ 26 % в живых прогонах (+3–6 МиБ). Пропажа `/scan` закрыта
  страховкой по legs (см. «Режим lidar»): без сканов точность — как у legs, после пропадания 15 с — ≤ 4,4 % офлайн.
- Возможные толчки корпуса через `/apply_force/trunk` в ТЗ не упомянуты — неизвестно.
