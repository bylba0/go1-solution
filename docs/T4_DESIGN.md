## 1. Задача и контракт (ТЗ_T4, раздел 6)
Judge сам ведёт робота (Gazebo Classic 11 + CHAMP, Highlevel, `/cmd_vel`, lockstep), участник только оценивает
фактическое положение и ориентацию корпуса.

| Топик | Тип | Направление |
|---|---|---|
| `/cmd_vel` | `geometry_msgs/Twist` | Judge → Simulator (**мы не публикуем**) |
| `/joint_states` | `sensor_msgs/JointState` | Sim → решение |
| `/imu/data` | `sensor_msgs/Imu` | Sim → решение |
| `/scan` | `sensor_msgs/LaserScan` | Sim → решение (пока не используем) |
| `/camera/...` (RGB-D 640×480, 15 Гц) | `Image`, `CameraInfo` | Sim → решение (не используем) |
| `/odom` | `nav_msgs/Odometry` | решение → Judge, `frame_id=odom`, `child_frame_id=trunk` |
| `/tf` | `tf2_msgs/TFMessage` | решение публикует `odom → trunk` |
| `/clock` | `rosgraph_msgs/Clock` | sim time |

- `/odom` и TF — **≥ 20 Гц sim**, согласованные поза и ориентация, корректные stamp и frame; NaN/Inf и
  ненормированные кватернионы запрещены. Начальная поза произвольна: Judge совмещает начальную оценку с истиной.
- Сценарий: неподвижная фаза → квадрат (4 прямых по 0,2 м/с, 4 поворота на 90° по 0,3 рад/с) → остановка →
  неподвижный интервал 10 с для дрейфа. Judge может замыкать курс по истине.
- Метрики: RPE — путь по истине режется на участки ≈ 1 м, ошибка `|Δp_odom − Δp_gt| / длина участка`, среднее по
  участкам; дрейф — изменение позы за 10 с неподвижности.
- Баллы (20): публикация `/odom` + TF ≥ 20 Гц — 3; RPE ≤ 50 % — 5; RPE ≤ 20 % — ещё 6; дрейф ≤ 0,10 м и ≤ 5° — 6.
- Запрещено: доступ к истине (`/odom/ground_truth`), воспроизведение заранее известной траектории вместо оценки.

## 3. Архитектура `src/go1_odometry`
Пакет из двух слоёв: расчёт без ROS (`core.py`, только numpy — тестируется на хосте) и тонкий ROS-узел (`node.py`).
Запуск: `/entrypoint.sh T4` → `go1_bringup/launch/t4.launch.py` → узел `go1_odometry` с `config/odometry.yaml`,
`use_sim_time=true`.

### core.py — `OdometryEstimator`
- **Входы** (сохраняют последнее валидное значение; NaN/Inf, неверная форма — отбрасываются и считаются в `rejected`):
  - `set_imu(t, quat, gyro=None)` — кватернион IMU (и угловая скорость для запасного режима `gyro`);
  - `set_joints(t, q)` — 12 углов в порядке `FR, FL, RR, RL × (hip, thigh, calf)`;
  - `set_contacts(t, mask)` — необязательная маска опоры (4 ноги), например по `/foot_force`.
- **Расчёт** `step(t)` — на таймере узла:
  1. Ориентация `odom ← trunk` = кватернион IMU (imu_link закреплён на trunk без поворота). При
     `heading_reference: world` курс мировой с первого сообщения.
  2. Прямая кинематика стоп по URDF сима (смещения бёдер ±0,1881 / ±0,04675 м, бедро 0,08 м, звенья 0,213 м)
     → положения стоп в осях `odom` относительно trunk.
  3. Вес опоры ноги `w = 1 − Δh / stance_height` (Δh — высота стопы над самой низкой, в обоих тиках); опорная стопа
     неподвижна в мире ⇒ смещение корпуса `Δx = −Δf`, взвешенное среднее по опорным ногам.
  4. ZUPT: стопы относительно trunk почти неподвижны и корпус не поворачивается ⇒ смещение 0 (защита дрейфа на стоянке
     от вибрации).
  5. Высота trunk — по опорным стопам + радиус стопы, сглаженная.
- **Выходы:** `position` (м, odom), `orientation` (x, y, z, w), `lin_vel`, `ang_vel` (в системе trunk, сглаженные),
  а также `stationary`, `weights`. Команды, траектория и истина не используются.

### node.py — `OdometryNode`
- Подписки: `/imu/data`, `/joint_states` (QoS RELIABLE, depth 10), `/clock` (через `use_sim_time`); `/foot_force` —
  только при `use_foot_force: true`. Колбэки только сохраняют сообщение; суставы сопоставляются по именам.
- Таймер расчёта `update_rate` (sim), публикация `/odom` и TF `odom → trunk` раз в `1/publish_rate` по sim time,
  с одним и тем же stamp (= текущее sim time); до прихода sim time и до первой валидной позы ничего не публикуется;
  публикуется только поза с конечными числами и |q| = 1 ± 1e-6.
- Переменные DDS (`ROS_DOMAIN_ID`, `RMW_IMPLEMENTATION`, `CYCLONEDDS_URI`, `ROS_LOCALHOST_ONLY`) не трогает.

### Параметры `config/odometry.yaml`
| Параметр | Значение | Зачем |
|---|---|---|
| `imu_topic`, `joint_states_topic`, `foot_force_topic` | `/imu/data`, `/joint_states`, `/foot_force` | входы; узел откажется стартовать, если имя не из белого списка |
| `odom_topic`, `odom_frame`, `base_frame` | `/odom`, `odom`, `trunk` | контракт ТЗ |
| `publish_tf` | `true` | TF `odom → trunk` обязателен |
| `update_rate` | 200 Гц sim | частота расчёта; суставы приходят ~990 Гц, берётся последнее — так узел лёгкий |
| `publish_rate` | 50 Гц sim | ТЗ: ≥ 20 Гц; запас в 2,5 раза |
| `use_foot_force` | `false` | `/foot_force` — необязательный сигнал; основной режим без него |
| `foot_force_order` | `[FL, FR, RL, RR]` | порядок каналов `/foot_force` (подобран по корреляции с кинематикой на bag A) |
| `foot_force_threshold` | 5,0 | порог «нога в опоре» по `/foot_force` |
| `pose_covariance_diagonal`, `twist_covariance_diagonal` | см. файл | ковариации в `/odom` (ТЗ их не оценивает) |
| `estimator.orientation_mode` | `imu` | кватернион IMU; `gyro` — запасной режим (интегрирование ω), по умолчанию не используется из-за вибрации |
| `estimator.heading_reference` | `world` | стартовый курс = мировой yaw IMU. Оценка тогда совпадает с миром и при совмещении Judge «поза», и «только положение» (см. раздел 7). `initial` — прежний режим (курс от 0) |
| `estimator.stance_height` | 0,005 м | мягкий порог «нога в опоре» по высоте над самой низкой стопой. При 0,02 м оценённый путь был занижен до ~0,75 от истинного (вес получали и низкие ноги в переносе, их движение «тормозит» среднее); с 0,005 м в среднее идут практически только стоящие ноги |
| `estimator.zupt_foot_speed` | 0,01 м/с | порог «стоим» по скорости стоп относительно trunk |
| `estimator.zupt_ang_speed` | 0,02 рад/с | порог «стоим» по угловой скорости (по разности ориентаций IMU, не по гироскопу) |
| `estimator.max_dt` | 0,1 с | при большем разрыве данных шаг не интегрируется (только пересброс опоры) |
| `estimator.foot_radius` | 0,02 м | радиус сферы стопы для высоты trunk над полом |
| `estimator.initial_height` | 0,29 м | z до первых `/joint_states` (робот стоит на ~0,29 м) |
| `estimator.height_alpha` | 0,02 | сглаживание высоты trunk |
| `estimator.twist_alpha` | 0,2 | сглаживание скоростей для twist |
| `estimator.contact_timeout` | 0,1 с | маска `/foot_force` старше — не используется |

## 4. Что запрещено и как это проверяется
- **Истина** (`/odom/ground_truth`, `/gazebo/*`, model/link states) в решении не читается. Белый список входов —
  `ALLOWED_INPUT_TOPICS = (/imu/data, /joint_states, /clock, /foot_force)` в `node.py`; узел падает при старте, если
  параметром задан другой топик.
- Тесты `test/test_node.py`: подписки узла ⊆ белого списка (с `/foot_force` и без); `/cmd_vel`, `/odom/ground_truth`,
  `/go1_contacts/FL` как параметр — отказ; в исходниках пакета нет запрещённых имён (cmd_vel, ground_truth, gazebo,
  go1_contacts, foot_contacts, camera, champ, model_states, link_states) и подписок вне `node.py`.
- `/cmd_vel` решение не публикует (воспроизведения командной траектории нет).
- Истина используется **только в стенде** (`tools/judge_t4.py`, `tools/dev_t4_offline_eval.py`) — для метрик и коррекции
  курса, как Judge. Стенд в образ не попадает. На живых прогонах стенд опрашивает граф: подписчик истины — только узел
  стенда, публикатор `/cmd_vel` — только стенд (ACCEPTANCE_T4).

## 5. Контакты — решение владельца (21.11)
- Опорные ноги определяются **по кинематике** из топиков контракта ТЗ (`/joint_states` + ориентация `/imu/data`).
- `/foot_force` — необязательный сигнал (параметр `use_foot_force`, по умолчанию выключен).
- `/go1_contacts/*` (`gazebo_msgs/ContactsState`) **не используем**, `gazebo_msgs` в образ не добавляем;
  `/foot_contacts` (champ_msgs) почти всегда False — тоже не используем.

## 6. Стенд самопроверки
### `tools/judge_t4.py` (только для разработки)
- **Режимы:** `live` — сим и решение уже запущены, стенд ведёт робота по пресету (`tz`: сторона 2 м, влево, коррекция
  курса по истине; `right`: 1,25 м, вправо; `tz_open`: 1,5 м без коррекции; `short`: 1 м), пишет `/odom`, TF и истину;
  `bag` — проигрывает bag разведки, оценку даёт образ решения (`--image`, `--cpus`) или заглушка (`--stub`);
  `reanalyze` — пересчёт метрик по `record.npz`.
- **RPE A** — разности в мировой системе после совмещения начальной позы (`--align pose`: перенос + поворот, ТЗ 6.2;
  `--align position` — только перенос, справочно как риск). **RPE B** — перемещение в системе начала участка своей
  траектории. Участки ≈ 1 м по горизонтальному пути истины, сглаженному 0,5 с; хвост короче 0,5 м не оценивается.
- **Дрейф** — изменение позы за 10 с неподвижности (положение и полный угол поворота).
- **Частота** — по `header.stamp` (sim), минимум окна 1 с; плюс проверки frame, NaN, |q|, монотонности stamp и
  `/odom ≡ TF` при одном stamp.
- Выход: `result.json` (PASS/FAIL по ТЗ и по порогам приёмки), `summary.txt`, `trajectory.png`, `record.npz`.
### `tools/run_t4_with_organizers_sim.sh`
Поднимает настоящий сим организаторов (`run_local.py --task T4`, headless, lockstep) и образ решения так же, как
судья (`--network host`, `/entrypoint.sh T4`), ограничивает CPU решения (`CPUS`, `docker update`), запускает
`judge_t4.py live` в том же домене, рядом — сторож памяти. Один сим за раз, запускать в tmux; прогон ~7–10 мин wall.

## 7. Ограничения и риски
- **Как Judge совмещает позу** (поворот или только положение) и что считает «путём» участка — `TODO(уточнить)` у
  организаторов. При курсе от 0 и старте с курсом ≠ 0 совмещение только положением давало RPE 40,5 % (bag B) и 50,3 %
  (bag C); с `heading_reference: world` — 11,1 % и 6,9 %, одинаково для обоих способов совмещения.
- **Длина стороны квадрата** и длительности фаз Judge неизвестны (ТЗ 6.3) — `TODO(уточнить)`; проверены 1,25–2 м.
- **RTF на ноутбуке ~0,2** (0,21–0,24 в живых прогонах): живой прогон долгий, статистика небольшая. Лимиты CPU/RAM
  в официальном прогоне неизвестны — проверяем с `CPUS=1.0`.
- **Лидар (этап 4, scan matching по `/scan`)** — отложен решением владельца; положение держится только на кинематике ног.
- Возможные толчки корпуса через `/apply_force/trunk` в ТЗ не упомянуты — неизвестно.
